# Неактивные пользователи Яндекс 360 с подразделениями

Скрипт `export_inactive_y360_users_with_departments.py` формирует список пользователей, у которых за выбранный период не обнаружена активность в сервисах Яндекс 360, и добавляет текущее подразделение каждого пользователя.

Скрипт использует три официальных метода:

- [статистика по пользователям](https://yandex.ru/dev/api360/doc/ru/statistics/get-user-statistics);
- [список сотрудников](https://yandex.ru/dev/api360/doc/ru/ref/UserService/UserService_List);
- [список подразделений](https://yandex.ru/dev/api360/doc/ru/ref/DepartmentService/DepartmentService_List).

Сторонние Python-библиотеки не требуются.

## Что делает скрипт

Во время запуска скрипт:

1. Постранично получает все подразделения организации.
2. Создает соответствие `departmentId → name`.
3. Постранично получает всех пользователей организации.
4. Создает соответствие `user_id → departmentId`.
5. Постранично получает статистику через `iteration_key`.
6. Определяет пользователей без активности за весь выбранный период.
7. Добавляет к каждому найденному пользователю `department_id` и `department_name`.
8. Сохраняет результат в CSV или JSON.

Отдельные API-запросы для каждого пользователя или подразделения не выполняются.

## Улучшенная архитектура для крупных организаций

Статистика обрабатывается сразу после получения каждой страницы. Скрипт не накапливает в памяти все строки за весь период.

Для каждого UID хранится только компактное состояние:

- обнаружена ли активность;
- сколько строк проверено;
- последняя строка с данными пользователя;
- последние непустые даты использования сервисов.

Поэтому потребление памяти зависит преимущественно от количества пользователей, а не от произведения количества пользователей на количество дней.

Например, для 2 000 пользователей и 15 дней API может вернуть около 30 000 строк. Скрипт последовательно обработает эти строки, но в памяти будет хранить состояние примерно для 2 000 UID.

Метод списка сотрудников допускает до 1 000 пользователей на одной странице. Для 2 000 сотрудников обычно потребуется два запроса к справочнику пользователей. Статистика и подразделения обрабатываются с учетом их собственной пагинации.

## Как определяется отсутствие активности

Пользователь попадает в итоговый отчет, только если во всех строках статистики этого пользователя одновременно выполняются условия:

1. Все числовые показатели Почты, Диска, Мессенджера и Телемоста равны `0` или `null`.
2. Даты последнего использования сервисов равны `null`, пусты либо находятся вне выбранного отчетного периода.

Проверяются все поля, начинающиеся с:

```text
mail_
disk_
messenger_
telemost_
```

Любое ненулевое значение сервисного показателя считается активностью.

Например, при отчете за 1–15 августа:

```json
"mail_last_usage_date": "2026-06-02"
```

не считается активностью за август. Если все счетчики равны `0` или `null`, пользователь попадет в отчет.

Значение:

```json
"mail_last_usage_date": "2026-08-07"
```

считается активностью, поскольку дата находится внутри отчетного периода.

> [!IMPORTANT]
> Отчет показывает отсутствие активности именно за выбранный период. Он не означает, что пользователь никогда не использовал Яндекс 360.

## Полученное письмо также считается активностью

Скрипт следует строгому критерию: все показатели должны быть равны `0` или `null`.

Поэтому пользователь не попадет в список неактивных при условии:

```text
mail_received_letters_count > 0
```

даже если пользователь не прочитал полученное письмо. Если требуется учитывать только осознанные действия пользователя, критерий следует изменять отдельно.

## Ограничения статистики

### Период отчета

Официальный метод статистики принимает период:

- минимум 1 день;
- максимум 3 месяца;
- даты в формате `YYYY-MM-DD`.

Начальная и конечная даты входят в проверяемый диапазон. Период больше трех месяцев отклоняется API с ошибкой `400 Bad Request`.

### Текущий день

Данных за текущий день в отчете нет: они становятся доступны на следующий день.

Поэтому скрипт не разрешает использовать текущую или будущую дату как конец периода. Если сегодня `2026-08-25`, последней допустимой датой будет `2026-08-24`.

### Отчет зависит от данных, возвращенных API

Скрипт не проверяет содержимое почтовых ящиков, Диска, Мессенджера или Телемоста. Он анализирует только строки и показатели, возвращенные методом статистики.

Если пользователь отсутствует в ответе статистики целиком, скрипт не может доказать отсутствие активности и не добавляет такого пользователя в итоговый файл.

### Поле `is_enabled` в статистике

Поле `is_enabled` из метода статистики не используется при отборе. Согласно документации статистики, оно означает наличие хотя бы одного действия за последние 30 дней.

Это поле сохраняется в результате только как справочная информация. Его не следует смешивать с одноименным полем справочника пользователей, которое характеризует статус аккаунта.

## Главное ограничение подразделений

Подразделение получается из текущего справочника организации во время запуска скрипта. API не возвращает историческую принадлежность пользователя к подразделению на дату статистики.

Например:

- отчет строится за 1–15 июня;
- в июне пользователь состоял в «Отделе продаж»;
- в августе пользователя перевели в «Отдел сопровождения»;
- скрипт запускается в августе.

В итоговом файле будет указано текущее подразделение — «Отдел сопровождения».

Также справочники пользователей и подразделений запрашиваются не одной атомарной операцией. Если администратор перемещает или удаляет пользователей и подразделения непосредственно во время запуска, возможны временные несовпадения.

Скрипт добавляет только непосредственное подразделение пользователя. Полный путь по иерархии родительских подразделений не строится.

## Если подразделение определить не удалось

Пользователь не удаляется из отчета. Поля `department_id` или `department_name` остаются пустыми, а причина записывается в `department_lookup_status`.

Возможные значения:

- `ok` — пользователь и подразделение найдены;
- `user_not_found` — UID из статистики отсутствует в текущем справочнике пользователей;
- `department_not_set` — у пользователя отсутствует `departmentId`;
- `department_not_found` — `departmentId` пользователя отсутствует в справочнике подразделений;
- `department_name_empty` — подразделение найдено, но его название пустое.

Количество таких несовпадений дополнительно выводится в терминале.

## Пагинация

Скрипт обрабатывает пагинацию всех трех методов:

- статистика — через `iteration_key`;
- пользователи — через `page`, `pages`, `perPage` и `total`;
- подразделения — через `page`, `pages`, `perPage` и `total`.

Обработка статистики заканчивается только после получения пустого `iteration_key`.

## Требования

- Python 3.9 или новее;
- доступ к `cloud-api.yandex.net` и `api360.yandex.net`;
- идентификатор организации Яндекс 360;
- OAuth-токен с необходимыми разрешениями.

Проверка версии Python:

```bash
python3 --version
```

В Windows:

```powershell
python --version
```

## Разрешения OAuth-приложения

Приложению требуются три разрешения:

```text
ya360_data:read_reports
directory:read_users
directory:read_departments
```

Если токен был получен до добавления новых разрешений, одного изменения настроек приложения может быть недостаточно. Получите новый OAuth-токен с обновленным набором прав.

Не записывайте токен в скрипт, README или репозиторий.

## Запуск в Windows PowerShell

```powershell
$secureToken = Read-Host "OAuth-токен" -AsSecureString
$tokenCredential = [System.Management.Automation.PSCredential]::new("oauth", $secureToken)
$env:OAUTH_TOKEN = $tokenCredential.GetNetworkCredential().Password
$env:ORG_ID = Read-Host "ID организации"

python .\export_inactive_y360_users_with_departments.py 2026-08-01 2026-08-15
```

Удаление переменных после работы:

```powershell
Remove-Item Env:OAUTH_TOKEN -ErrorAction SilentlyContinue
Remove-Item Env:ORG_ID -ErrorAction SilentlyContinue
Remove-Variable secureToken, tokenCredential -ErrorAction SilentlyContinue
```

## Результат

По умолчанию создается CSV:

```text
inactive_y360_users_2026-08-01_2026-08-15.csv
```

CSV использует:

- кодировку UTF-8 с BOM;
- разделитель `;`;
- одну строку на пользователя;
- сортировку по подразделению, ФИО, nickname и UID.

Если неактивные пользователи не найдены, файл все равно создается и содержит заголовки.

## Поля итогового файла

- `user_id` — UID пользователя;
- `nickname` — логин;
- `account_type` — тип аккаунта;
- `name` — ФИО из статистики;
- `department_id` — текущий идентификатор подразделения;
- `department_name` — текущее название подразделения;
- `department_lookup_status` — результат сопоставления подразделения;
- `is_admin` — признак администратора из статистики;
- `is_manager` — признак менеджера из статистики;
- `is_enabled` — справочный признак активности из статистики;
- `report_start_date` — начало периода;
- `report_end_date` — конец периода;
- `statistics_rows_checked` — количество строк статистики пользователя;
- `mail_last_usage_date` — последняя непустая дата Почты;
- `disk_last_usage_date` — последняя непустая дата Диска;
- `messenger_last_usage_date` — последняя непустая дата Мессенджера;
- `telemost_last_usage_date` — последняя непустая дата Телемоста.

## Возможные ошибки

### `400 Bad Request`

Проверьте:

- формат и порядок дат;
- ограничение периода до трех месяцев;
- значение `--limit`;
- корректность `ORG_ID`.

### `401 Unauthorized`

Токен отсутствует, истек, отозван или передан некорректно.

### `403 Forbidden`

Проверьте наличие всех трех разрешений:

```text
ya360_data:read_reports
directory:read_users
directory:read_departments
```

После изменения разрешений получите новый OAuth-токен.

### `404 Not Found`

Организация не найдена либо недоступна владельцу токена.

### `429 Too Many Requests` и ошибки `5xx`

Скрипт автоматически повторяет запрос до четырех раз с увеличивающейся задержкой. Если ошибка сохраняется, повторите запуск позже.

## Безопасность

- Не добавляйте токен в исходный код.

- Не сохраняйте токен в файле, который может попасть в Git.
- При подозрении на компрометацию отзовите токен и получите новый.

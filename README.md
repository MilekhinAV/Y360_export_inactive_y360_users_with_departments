# Неактивные пользователи Яндекс 360 с подразделениями

Скрипт `export_inactive_y360_users_with_departments.py` классифицирует пользователей по датам использования Почты, Диска, Мессенджера и Телемоста, учитывает дату создания аккаунта и добавляет текущее подразделение. Результат сохраняется в CSV или JSON. Скрипт только читает API и формирует отчёт; аккаунты не изменяет.

## Быстрый старт

Нужны Python 3.9+, идентификатор организации и OAuth-токен с разрешениями:

```text
ya360_data:read_reports
directory:read_users
directory:read_departments
```

Используется стандартная библиотека Python и системная база часовых поясов. Если база недоступна (например, в Windows), установите её:

```bash
python -m pip install tzdata
```

Скачайте **полный файл** скрипта из репозитория. В macOS / zsh откройте терминал в папке со скриптом:

```zsh
read -s "OAUTH_TOKEN?OAuth-токен: "
echo
read "ORG_ID?ID организации: "
export OAUTH_TOKEN ORG_ID

python3 export_inactive_y360_users_with_departments.py 2026-08-01 2026-08-31 --all-users
```

Для первого запуска рекомендуется `--all-users`: он показывает всех пользователей, причины классификации и проблемы данных. Без флага в файл попадают только кандидаты — `inactive` и `no_activity_recorded`.

Если локально файл переименован в `export_inactive_y360_users.py`, используйте это имя в команде. В репозитории сохранено исходное имя с `_with_departments`.

### Linux / Bash

```bash
read -s -p "OAuth-токен: " OAUTH_TOKEN
echo
read -p "ID организации: " ORG_ID
export OAUTH_TOKEN ORG_ID
python3 export_inactive_y360_users_with_departments.py 2026-08-01 2026-08-31 --all-users
```

### Windows / PowerShell

```powershell
$secureToken = Read-Host "OAuth-токен" -AsSecureString
$tokenCredential = [System.Management.Automation.PSCredential]::new("oauth", $secureToken)
$env:OAUTH_TOKEN = $tokenCredential.GetNetworkCredential().Password
$env:ORG_ID = Read-Host "ID организации"
python .\export_inactive_y360_users_with_departments.py 2026-08-01 2026-08-31 --all-users
```

Не записывайте токен в код, команды с буквальным значением или файлы репозитория. После завершения можно очистить переменные: `unset OAUTH_TOKEN ORG_ID` в zsh/Bash; в PowerShell — `Remove-Item Env:OAUTH_TOKEN, Env:ORG_ID` и `Remove-Variable secureToken, tokenCredential`.

## Формула и границы периода

Обе даты входят в отчёт. Начальная дата — граница `cutoff`. Проверка выполняется с точностью до календарного дня:

```text
кандидат = дата_создания < start_date
           И для каждого сервиса:
               последняя_известная_дата < start_date ИЛИ дата пустая
```

Дополнительно кандидат должен пройти проверки качества данных и не попасть в исключения.

Для периода `2026-08-01 — 2026-08-31`:

- аккаунт создан до 1 августа;
- ни одна валидная дата использования не находится в августе;
- дата ровно 1 августа считается активностью;
- аккаунт, созданный 1 августа, считается новым;
- старая дата Почты и пустые даты остальных сервисов допускают статус `inactive`.

`createdAt` переводится в `--timezone` (по умолчанию `Europe/Moscow`), затем берётся календарная дата. Даты статистики используются как возвращены API: часовой пояс в запрос статистики не передаётся. Это выбранное правило отчёта, а не гарантия часового пояса агрегации API.

Это оценка за выбранный период, а не автоматически «за последние N дней от сегодня». Для текущего контроля задавайте период, заканчивающийся вчера. Сегодняшний и будущие дни запрещены в часовом поясе отчёта.

## Статусы и порядок проверок

Проверки выполняются в следующем порядке; первое подходящее условие определяет статус:

| Статус | Условие / причина |
|---|---|
| `insufficient_data` | UID статистики отсутствует в текущем справочнике: `user_not_in_directory` |
| `excluded` | `isRobot=true`: `service_account`; `isDismissed=true`: `dismissed`; `isEnabled=false`: `blocked` |
| `insufficient_data` | Нет корректного `createdAt` с часовым поясом: `invalid_or_missing_created_at` |
| `excluded` | Создан после конца отчёта: `created_after_report_end` |
| `new_account` | Создан в отчётном периоде: `created_on_or_after_cutoff` |
| `insufficient_data` | Нет строк статистики: `no_statistics` |
| `active` | Хотя бы одна валидная дата использования внутри периода: `usage_in_period` |
| `insufficient_data` | Ошибки строк, полей или неполное покрытие дней |
| `inactive` | Есть известные даты, все раньше начала: `all_known_usage_before_cutoff` |
| `no_activity_recorded` | Все даты явно пустые: `all_usage_dates_empty` |

`active` может сопровождаться проблемами в `statistics_status`: найденной активности достаточно, чтобы исключить пользователя из кандидатов, даже если остальные данные неполны. Новые и исключённые аккаунты тоже могут иметь неполную статистику.

## Проверки качества

- Отсутствующее поле отличается от явного `null` или пустой строки.
- Непустые даты должны разбираться как ISO-даты.
- Дата использования после конца отчёта считается аномалией и не включается в агрегированную последнюю дату.
- Поле `date` строки должно быть валидным и находиться внутри всего периода отчёта.
- Повтор даты строки для одного UID отмечается как `duplicate_row_date`.
- Для признания старого аккаунта кандидатом требуется по одной строке на каждый день периода. Пропуски дают `incomplete_daily_coverage`.

**Ежедневное покрытие — консервативное допущение скрипта.** Документация не гарантирует ежедневные строки для каждого аккаунта. Перед использованием результатов проверьте это на реальных ответах API. Если API выдаёт разреженные данные, такие пользователи останутся в `insufficient_data`, а не будут автоматически признаны неактивными.

Причины ошибок также включают `invalid_row_date`, `missing_usage_field:<поле>`, `invalid_usage_date:<поле>` и `usage_after_report_end:<поле>`. Несколько причин объединяются через `;`.

Пустые даты означают только отсутствие зафиксированной активности в полученных данных. Они не доказывают, что человек никогда не использовал сервисы.

## Что считается активностью

Для классификации используются только:

```text
mail_last_usage_date
disk_last_usage_date
messenger_last_usage_date
telemost_last_usage_date
```

Числовые счётчики не участвуют в отборе. В частности, получение письма само по себе больше не исключает пользователя из кандидатов. Поле `mail_received_in_period` отдельно показывает, было ли ненулевое значение счётчика полученных писем в обработанных строках с корректной датой. При неполной статистике `false` не доказывает отсутствие писем за весь период.

Точный состав событий, обновляющих даты использования, и семантика пустот не раскрыты в документации метода. Счётчики могут отражать действия, не согласованные с датами; текущий режим следует именно формуле по датам и не сверяет такие противоречия.

`is_enabled` из статистики — справочный признак активности за последние 30 дней. Он не используется для отбора и не равнозначен `directory_is_enabled`, который отражает текущую блокировку аккаунта.

## Параметры и результаты

```bash
# Только кандидаты, CSV
python3 export_inactive_y360_users_with_departments.py 2026-08-01 2026-08-31

# Все статусы, JSON, заданный путь
python3 export_inactive_y360_users_with_departments.py 2026-08-01 2026-08-31 --all-users --format json --output users_august.json

# Справка
python3 export_inactive_y360_users_with_departments.py --help
```

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `start_date`, `end_date` | Обязательны | Границы периода `YYYY-MM-DD` |
| `--all-users` | Выключен | Вывод всех статусов |
| `--format` | `csv` | `csv` или `json` |
| `--output` | Автоматическое имя | Путь файла, существующий файл перезаписывается |
| `--timezone` | `Europe/Moscow` | Календарная дата создания и проверка текущего дня |
| `--limit` | `1000` | Положительное число записей на страницу статистики |
| `--timeout` | `60` | Положительный тайм-аут запроса в секундах |

Имена по умолчанию: `inactive_y360_users_2026-08-01_2026-08-31.csv` или `all_y360_users_2026-08-01_2026-08-31.csv`. Для JSON расширение меняется на `.json`.

CSV: UTF-8 с BOM, разделитель `;`, заголовки даже при пустой выборке. JSON: объект `{"items": [...]}`. Сортировка — подразделение, имя, UID. Терминал показывает число пользователей по каждому статусу до фильтрации кандидатов.

### Поля экспорта

| Поля | Содержание |
|---|---|
| `user_id`, `nickname`, `name`, `account_type` | Идентификация пользователя; имя дополняется из справочника при отсутствии в статистике |
| `department_id`, `department_name`, `department_lookup_status` | Текущее непосредственное подразделение и результат сопоставления |
| `is_admin`, `is_manager`, `is_enabled` | Справочные поля из последней обработанной по дате строки статистики |
| `created_at`, `cutoff_date`, `report_timezone` | Исходный `createdAt`, граница отбора и выбранный часовой пояс |
| `report_start_date`, `report_end_date` | Границы отчёта |
| `classification`, `classification_reason`, `inactive_candidate` | Статус, причина и включение в список кандидатов |
| `statistics_rows_checked`, `statistics_days_checked`, `statistics_status` | Число строк, уникальных валидных дней и качество данных |
| `last_activity_date` | Максимум валидных дат использования, не выходящих за конец отчёта |
| Четыре поля `*_last_usage_date` | Максимальная валидная дата каждого сервиса среди обработанных строк |
| `directory_is_enabled`, `is_robot`, `is_dismissed` | Текущие признаки из справочника |
| `mail_received_in_period` | Признак ненулевого счётчика полученной почты; не число писем |

`department_lookup_status`: `ok`, `user_not_found`, `department_not_set`, `department_not_found`, `department_name_empty`. Проблема подразделения сама по себе не исключает кандидата.

## API и ограничения

Используются официальные методы:

- [Статистика по пользователям](https://yandex.ru/dev/api360/doc/ru/statistics/get-user-statistics).
- [Список сотрудников](https://yandex.ru/dev/api360/doc/ru/ref/UserService/UserService_List).
- [Список подразделений](https://yandex.ru/dev/api360/doc/ru/ref/DepartmentService/DepartmentService_List).

Один запрос статистики допускает период до трёх месяцев; скрипт делит любой период на непересекающиеся интервалы до 28 дней, обрабатывает `iteration_key` каждого интервала и объединяет состояния пользователей. Разбиение не гарантирует доступность старой истории на стороне сервиса.

Справочники загружаются постранично, без запроса на каждого пользователя. Полные строки статистики не накапливаются, но набор уникальных дней хранится для каждого UID: память зависит и от количества пользователей, и от длины периода.

Подразделения и статусы аккаунтов берутся на момент запуска, поэтому исторический отчёт не восстанавливает организационную структуру или блокировки на прошлую дату. Данные справочников и статистики не являются атомарным снимком. Проверяются только четыре перечисленных сервиса.

### Ошибки запуска

- `IndentationError` на первой строке: проверьте, что скачан весь Python-файл, а не фрагмент функции.
- Неизвестный часовой пояс: проверьте `--timezone`; при отсутствии системной базы установите `tzdata`.
- `400`: проверьте даты, ID организации и `--limit`.
- `401`: проверьте срок действия токена.
- `403`: проверьте разрешения токена и доступность статистики для организации.
- `404`: организация не найдена или недоступна.
- `429` и `5xx`: скрипт делает до четырёх повторных попыток, затем завершает работу с ошибкой.

## Тесты

```bash
python3 -m unittest -v test_y360_inactivity.py
```

Тесты используют синтетические данные и подставные ответы, не требуют токена и не обращаются к API. Покрывают границы дат, смешанные пустоты, получение писем, исключения, ошибки данных, пропуски и дубликаты дней, соединение со справочником, разбиение периода и пагинацию. Проверка на реальной организации остаётся отдельным этапом.
